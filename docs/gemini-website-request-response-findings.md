# Gemini website request/response findings

Piece 1 of the Gemini-website carryover (`~/.worker-state/briefs/gemini-website-job-carryover.md`), 2026-09-14. Read-only against `identify/src/providers/gemini.ts`'s 13 numbered header assumptions and `identify/src/providers/gemini-grounded.ts`'s `walkSteps`, synthesized against what pieces 2 through 7's website sessions actually showed (`identify/test/fixtures/gemini-website/piece2` through `piece7`). No new prompt was sent for this piece; every other piece's chat session is the evidence.

The website (`gemini.google.com/app`) is a different product surface from the Interactions API `gemini.ts` and `gemini-grounded.ts` call. It shows rendered chat output, never a raw request or response body. That ceiling holds for every one of the 13 assumptions below: none of them can be confirmed or contradicted by website testing. What the website testing DID produce is real evidence about model behaviour given the real prompt text, which is a different and narrower kind of confidence than "the wire format is right."

## The step types (`gemini-grounded.ts`'s `walkSteps`)

`walkSteps` reads four step types: `google_search_call` (search queries issued), `google_search_result` (carries `search_suggestions` HTML, taken byte for byte), `code_execution_call` (carries the executed code, read from either `arguments.code` or `executableCode.code` since the two doc pages disagree), and `model_output` (the answer text plus `url_citation` annotations). None of these are literally observable as JSON on the website — the closest equivalents are visual:

- A search chip or "Searching the web" indicator under a reply is the website's rendering of something like a `google_search_call`/`google_search_result` pair. Piece 3 (barcode lookup) showed the "Searching the web" indicator and no citation chip in the final answer, consistent with a search having run and having found nothing to cite (a genuine no-record answer) — but this is inference from UI chrome, not a look at the actual step list or its `search_suggestions` field.
- A "Code" block with a printed result is the website's rendering of something like a `code_execution_call`/result pair. Piece 5 (from the prior session) exercised this directly: the code shown to have run matched a real local `python3` run of the same function byte for byte on every number, which is real evidence the model can execute Shin's fixed function correctly and report a correct result — but the website never showed the raw `executableCode.code` field name or structure, only rendered code and output, so `walkSteps`'s exact field-reading logic (`arguments.code` vs `executableCode.code`) remains unconfirmed either way.
- `url_citation` annotations (with `start_index`/`end_index` into the answer text) have no visible website equivalent at all — the website shows citations as separate chips/links, not as inline offsets into the text. This is a real gap: even if citations appear correctly on the website, there is no way to check the annotation SHAPE `walkSteps` expects.

## What this testing actually adds, beyond "unverifiable"

Nothing above should be read as pessimistic about pieces 2 through 7's value — they answer a different, narrower question than piece 1's wire-format assumptions: given the real prompt text, does Gemini's content behave sanely? On that question:

- Piece 2: photo-only identification recovered brand and (when the label text was in frame) name correctly, and correctly declined rather than guessed when the crop did not contain the text. No hallucinated fields.
- Piece 3: a genuine catalogue-miss barcode was correctly reported as not found, not invented.
- Piece 4: found a real content-reliability risk worth carrying into whoever builds the real parsing path — a grounded, schema-shaped ask can come back with markdown-wrapped URLs embedded in JSON string values (confirmed genuine by visual inspection, not a text-extraction artifact) and, on the website at least, with more than one candidate JSON block in a single reply. `gemini-grounded.ts`'s own `parseJson` helper (fenced-block-preferring, falls back to first-`{`-to-last-`}`) would likely still recover a valid object from a reply shaped like piece 4's — its regex prefers the fenced block, which in piece 4's case was the complete one — but a markdown-wrapped URL landing in a `url` field would still reach calling code as a `string` that is not a bare URL. Worth a defensive check wherever `url` fields from this path are used directly (opened, compared, deduplicated), regardless of whether the two-block behaviour itself turns out to be website-only.
- Piece 5: exact numeric agreement between Gemini's executed code and a real local run, on the same function and inputs — real evidence the code-execution path can be trusted to run Shin's function unmodified, at least in this one case. Also surfaced a real gap: `verdictResubmissionRequest`'s prompt never sends the shelf item's own size, only its price, which the model then infers from the offers list.
- Piece 6: a real, sharp quality cliff for this photo/label between what stands in for `medium` and `high` resolution — evidence worth weighing against assumption 5's default (not a decision, per ruling 12).
- Piece 7: no genuine field-level contradiction arose across four real frames of one item; disagreement in this run was entirely "some frames had the text in view, some did not," which agreement-across-frames (ruling 11) handles correctly without a second model call.

## What only a real key resolves

Every row marked unverifiable above, in full: the endpoint path, the auth header form, the exact request body shape, the `input` role-tagged-message structure, the image part shape and whether `resolution` is honoured at all, the 20 MB ceiling behaviour, `thinking_level`, the `steps` array and `model_output`/`url_citation` shapes, the real usage/token field names, the refusal/block-reason wire location, the `OTHER`-finish-reason classification, cache-breakpoint handling, and which model ids the API actually accepts. Also unresolved: whether the real structured-output endpoint (schema-constrained, not free chat) can ever produce the two-concatenated-JSON-blocks behaviour piece 4 found on the website, since the website is a free chat surface with no schema enforcement and the real path is not.
