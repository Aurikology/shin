#### CONFIRMED

##### C1. "Not this" pick, then typing a price, ends on a failure sheet
- Shopper: scans or types a name, taps "Not this", picks the right product from the list, types its shelf price.
- Should: the verdict for the picked product.
- Actually: the pick opens a pad with gtin set (camera.js:5961-5966, data-pick-code handler 5940). Confirm calls proceed() -> api.price with `gtin: item.scannedGtin ?? item.gtin` (camera.js:5328, ~5385). Client shows the failure sheet. (The barcode-scan case is spared by the R-36 branch at camera.js:5957, which uses askPriceFirst.)
- Caveat: reachability of "Not this" on a typed-name answer was read from code, not run.

##### C2. "What did you do?" outcome row can never appear
- Shopper: told a price is high, should be asked Bought elsewhere / Price matched / Bought here / Not bought.
- Actually: outcomeRow() camera.js:1345 only renders at camera.js:1478 when saysCheaperElsewhere() (camera.js:1338) is true: zone 'over_your_line' or priceMatch.line. - Result: postScanOutcome (api.js:528) and route /api/scan/:id/outcome (server.ts ~2672-2693) are unreachable from a shopper.

##### C3. Gemini sheet content sections are always empty

##### Why each class fails, with file:line

1. **Barcodes typed as digits (100%).** Already filed, counted for the total. The route builds `{ text, limit, vectors }` and never `gtin` (`app/server.ts:3009`), so the barcode branch at `search.ts:1353` cannot run for a typed number. The digits then go through FTS as a word, and the barcode is in `code`, not in an indexed column, so nothing matches. The padding logic that would have fixed 12 vs 13 digits (`search.ts:1048`) is never reached.

2. **Typos (38% empty, 69% failed).** There is no fuzzy step anywhere. Retrieval is FTS5 with `unicode61 remove_diacritics 2` and nothing else (`schema.ts:183`): exact tokens, plus one prefix wildcard on the LAST token only (`search.ts:683-685`). The semantic arm that would absorb "mlik" is off (`vectorsOn:false`, `app/server.ts:327`). So `mlik`, `cheerois`, `yoghrt`, `colgte`, `ketchp`, `oreeo` are empty. The five typo queries that did not fail were saved by luck: a catalogue row that contains the same typo ("Honey Nut Cherios", "Chesse stick", "Sourdough Bred", "CHEES", "shampo"), or by the prefix wildcard (`toothpast`). Typos that happen to be a real word are worse than empty: "tied" returns Tiedemanns tobacco, "eggz" returns a toy, "buter" a Buter Pecan row, "peanut buter" returns Buter Pecan above any peanut butter.

3. **Abbreviations (67%).** No synonym or expansion table exists in the query path; "oj" returns Ojibwa blend, "pb" returns PB2, "tp" returns "Ah tput cru". "pc ketchup" answers with Heinz and Selection ketchup, not President's Choice. "pc" alone never answers: the token `"pc"*` is a prefix on a two-letter string, the match set is enormous, and `ORDER BY bm25` has to score all of it (`search.ts:1086-1090`, `search.ts:1187-1192`) until a limit of about 5 s fires (observed at 5.00 to 5.05 s on three calls; I did not locate the limit in code, so the link between the huge prefix scan and the timeout is inferred from the comment at those lines, not proven). `kd` works only because the catalogue has a literal "KD" brand.

4. **Sizes in the query (43% failed).** Size words are just tokens. The route never turns "2L" or "454g" into `sizeValue/sizeUnit` (`server.ts:3009`), although the engine can use them (`search.ts:438-439`, `pinTier` at `975-981`). With 2+ words the strict AND pass needs 5 hits (`search.ts:1121-1122`); if it gets fewer, the OR pass runs (`search.ts:1138`) and BM25 rewards the rarest token, which is the size. So "milk 2L" and "2% milk 2L" lead with "2L 7up"; "butter 454g" leads with a Buenas Cassava Cake 454g; "rice 1 kg" leads with a De'Longhi "KG89" (the tokenizer splits "1 kg" into "1", dropped for being one character at `search.ts:676`, and "kg", a prefix on a rare token). "flour 2.5kg" leads with Urad Flour 800 g. Where a size query worked ("coke 500ml", "eggs 12", "orange juice 1.89L"), it was because the size sits in the product's name text; quantity is never compared. "eggs dozen" returns 18-packs.

5. **Missing letters (40%).** Works only when the missing letter is in the LAST word and the stem is not a prefix of something else (`mil` finds milk, `colgat`, `cheerio`, `toilet pape`, `yogur`). Fails when the damaged word is not last ("orang juice" returns Blue Orang) or the stem is another word's prefix: `butte` returns Butterfinger first, `tid` returns Pineapple Tidbits, `pasa` returns Que Pasa. Cause is the same: wildcard on the last token only (`search.ts:683-685`), no edit distance.

6. **Punctuation and symbols (23% failed).** The tokenizer splits on anything that is not a letter, digit or ".", then drops every token of one character (`search.ts:671-677`). "m&m's" becomes m, m, s, all dropped, so zero tokens and an immediate miss (`search.ts:1111`); "m & m" the same; "2%" and "1%" the same. "m&ms" keeps only "ms" and returns a Lenovo part and Ms Vickies; "mms" a Matrox card. Apostrophes also split ("Nature's" is "nature" + "s" in the index), so a shopper who omits the apostrophe loses: "natures path" returns chocolate strawberries, "kelloggs" misses every "Kellogg's" row it should hit. Quotes, commas and "!" are handled (stripped at `search.ts:674-675`); "&" vs "and" is not unified ("ben and jerrys" appears to work only because "ben" alone carries the OR pass; "Uncle Ben's" is third).

7. **Plurals (6% top-1 wrong, but lists differ).** No stemmer (`schema.ts:183`). The prefix wildcard helps singular to plural only ("egg" reaches "Eggs") and never plural to singular ("eggs" cannot reach rows named "Egg"). Top-1 is plausible for 15 of 16 ("apple" leads with a Larabar Apple Pomme bar), but singular and plural return different shelves: of the five rows each pair returns, the two forms share on average 1.4 of 5 codes (13 of 45), 0 for chip/chips and apple/apples, same top-1 for only tomato/tomatoes. A shopper typing the other form gets a different list, not a worse one.

8. **Usability of what comes back (all classes).** Only 33% of top-1 rows have brand and size, 57% of lists repeat a name. The dedupe key is brand + name + size (`search.ts:772-793`), so "Cheerios / - / -", "Cheerios / Cheerios / -" and "Cheerios / Plus, Cheerios / -" all survive as three rows. That is a data-quality problem the ranking does not fix: nothing ranks rows carrying brand and size above bare ones (`pinTier` only rewards agreement with a pinned brand or size the route never supplies). "deodorant" is the already-filed example of the same thing.

9. **Things that held up.** Capitalisation, extra spaces, quotes and trailing punctuation: 9 of 9, identical lists for "milk", "MILK", "mIlK", "  milk  ". French basics: 14 of 14 plausible (accent folded: "cereales" and "céréales" both work; `schema.ts:183`), but this only works because French-named rows exist; a French word against an English-only row was not measured here. Brand + product queries: 13 of 14 right.

## Family 5: verdicts versus evidence (D-270)

### Family 5: verdict overclaims and self-contradictions (Pexi, C:\shin)

Read-only. Method: read estimate.ts, range.ts, catalogue-first.ts, server.ts identify and typedVerdict branches, camera.js verdict rendering, verdict-chart.js, history-answer.js, catalogue-range.js, ui-strings.js. 6 live priced scans were used (0066721005694 twice, 0068100084245 once, typed "Kraft dinner", "cereal", "milk"); raw JSON is in the scratchpad (oreo.json, oreo2.json, kraft.json, kd.json, cer.json, milk.json).

Tags: CONFIRMED-LIVE = seen in a live response. CONFIRMED-CODE = proven by reading the code and arithmetic, not run. SUSPECTED = plausible from code, not shown.

Already filed, not repeated: "Fairly sure" beside "Few prices"; "7 prices from 7 shops" above 12 rows; AI estimate alone giving Bad price (Kraft dinner 3.3x, deodorant 43%); typo search "$2.78 to $36.02, a broad guess".

#### A. Overclaims (answer stronger than evidence)

##### A1. A typed generic or short name is silently resolved to ONE specific product, then judged with "Certain" confidence. CONFIRMED-LIVE (3 of 3 typed probes)
- "milk" (shelf $15.00) answered as "Coconut Milk 400ml", basis own_prices, n=7, confidence high, zone bad, +410%, beyond high.
- "cereal" (shelf $5.00) answered as "Cocoa Loops 261g", n=3, confidence high, zone reasonable.
- "Kraft dinner" (shelf $9.00) answered as "Kraft Dinner 12 Pack 12x200g" (2.4 kg), n=4, confidence high, zone GREAT -35.7%. A shopper holding a 225 g box ($1.50 to $2.50) is told a $9 price is great, against a $13.99 median that belongs to a 12 pack.
- Shopper sees: a product name they never typed, tier word at full strength, "Certain". Nothing says "we guessed which product you meant".
- Cause: app/server.ts ~1217-1249: for an ambiguous typed name `resolution.row` is null yet `match = lookupOwnPrices(text)` still supplies a code, and catalogueFirstBarcode prices that guessed product (the comment says ambiguous should answer from the typed words alone). Sibling: matchTextVerdict (server.ts ~1685-1721) judges the top-1 text match with the shelf price regardless of match score and with no size check.
- Touches: every typed or voice search, any short or generic word, any name with several pack sizes. This is the biggest sibling of the filed sizeless "Kraft dinner" bug: the live path does not even reach the AI estimate, it picks a wrong-size real product and calls it Certain.

##### A2. The zone word ignores uncertainty. CONFIRMED-CODE (explains filed AI-estimate "Bad price" cases)
- Shopper sees: "Bad price, N% over" / "Great price" at full strength on the weakest evidence (AI typical range, category prior, department prior, brand markup, national average, other-size, 1-shop blend).
- Cause: price/src/estimate.ts zoneOf (863-868) uses centre and flat percent lines only. The only softening is categoryOnlyLines widening (850-859, applied 1447-1448), and it applies only to leaf_category and parent_category with default lines. Client: headline is always the zone word (camera.js 1799-1800); distFace (history-answer.js 26-38) softens great and good to a "fair" face at low confidence but "bad" keeps the walk-away face and red tier (verdict-chart.js 336) at any confidence; confidence appears only in the half detent (camera.js 1869).
- Touches: claude_typical, category_prior, department_prior, brand_markup, national_average, other_size, thin own_prices.

##### A3. Confidence word is not tied to how wide the band is. CONFIRMED-LIVE
- "Kraft dinner" probe: confidence high ("Certain") while spreadFrom is "prior" (the empty prior, sigma 0.51) and the bell is $7.24 to $27.03, a 3.7x spread.
- "milk" probe: confidence high, sigma 0.548, bell $1.46 to $5.94 (4x).
- Cause: estimate.ts 1434-1440: own_prices is high with >=3 fresh shops, medium otherwise; other_size always medium; independent of sigma. With a missing own spread, sigma falls to category prior or EMPTY_PRIOR (1401-1423). old_prices and other_region do not lower confidence (only !ownAged and !old_prices are checked, other_region is not checked at 1435); leaf_category n>=20 medium ignores old_prices.

##### A4. Band wider than every price actually seen. CONFIRMED-LIVE
- Kraft peanut butter 1 kg: all 12 dots lie $5.97 to $8.49, yet the shaded "8 in 10 prices" runs $4.81 to $11.85 (low end 19% under the cheapest ever seen, high end 40% over the dearest), n=7 high confidence.
- Coconut milk: all dots $1.75 to $3.99, band $1.46 to $5.94.
- Cause: sigma is not the spread of the own prices; it is mixed with the category or prior spread (estimate.ts 1401-1423, 1140 blend path). The shopper sees a bell visibly wider than the dots drawn on it, which reads as "Pexi does not know".

##### A5. Centre is a blend, so the "typical price" matches no price shown. CONFIRMED-LIVE
- Oreo 303 g: both dots are $4.99, one shop. Centre shown $5.01, range card says $3.58 to $7.02 (median $5.01) built from category spread. Shopper at $3.00 gets "Great price, -40%" and at $6.20 gets "Bad price, +23.8%" off a single shop observation, "Medium" confidence.
- Kraft peanut butter: centre $7.55 vs the range card median $6.99 (see B1); 5 of the 7 regular shop prices are at or below $6.99.
- Cause: estimate.ts 1140 `mu = (n*muOwn + 1*mu_cat)/(n+1)`, with the blend using catStats even when that pool was too wide (tooWide not checked for the blend) and, for an item without size, an unscaled any-size pool (poolPoints target null) with no size_assumed note.

##### A6. Category and department priors compare across sizes. CONFIRMED-CODE
- estimate.ts 1354-1356 poolPoints(..., null, false) mixes sizes per item, so a 2 kg item is ranked against a 100 g item and still gets a zone (priors are suppressed only for too_thin / noPrices, 1385-1395, 1467). This is the broad-guess family of filed case (4) with a zone word attached. Not run live (no unknown-name probe left that I judged different from the filed one).

##### A7. AI range's `unit` and `confidence` are dropped in the verdict path. CONFIRMED-CODE
- range-ask.ts returns unit ("one 500 mL bottle / each") and confidence (low/medium/high); distribution.ts onceAsk.askClaude returns only lowCents/highCents/currency, so estimate.ts claude_typical treats a per-kg or per-bottle range as this item's price. The range-only sheet refuses to place a shelf price when `unit` is set (catalogue-range.js 90) but the verdict path has no such guard. The prompt asks for "exactly the size named" and passes "Size: not stated" for sizeless items, so the guess is for an unknown size and the shopper's price is still judged (root of filed 3.3x Kraft dinner).

##### A8. "Nx the typical price" on `beyond`. SUSPECTED (milk probe shows the pattern)
- `beyond` is past p1/p99 of the bell (estimate.ts 902). With the 0.05 sigma floor (several identical shop prices) a price only ~12% over is labelled "1.1x the typical price"; with wide AI or sizeless bells, a multiple like 5x ("milk": +410%) is shown next to a Bad word as if measured (verdict-chart.js multiple; camera.js 1738).

##### A9. Store-only / sale-only item gets a regular-price verdict. SUSPECTED
- catalogue-first.ts 679 shows a verdict when `dots.length > 0`, which counts sale-only dots, so an item seen only on sale is judged from its category as if regular.

##### A10. other_region note rarely fires, and does not lower confidence. SUSPECTED
- otherRegion only when both item.region and row.region are provinces (estimate.ts 771-777, 1112-1121). Open Prices rows keep a shop id in `region` so they never count; with no client region the note never appears. When flagged, confidence can still be high (see A3).

##### A11. biggerPack note shows a price from any store, any age, any region. SUSPECTED
- estimate.ts 1153-1161 takes the lowest per-unit among same-product packs >2x, up to 2 years old, any region, with no date or place, and the item's own per-unit is never shown beside it ("a bigger pack ... works out to $0.55 per 100 g").

#### B. Contradictions between parts of one result screen

##### B1. Range card and bell disagree on the same product. CONFIRMED-LIVE
- Kraft peanut butter 1 kg: range card (this_product) says $6.29 to $8.49, median $6.99, n=7; the bell on the same answer centres on $7.55 with band $4.81 to $11.85. Kraft Dinner 12 pack: range median $13.99 (n=4) vs centre $13.99 but band $7.24 to $27.03, and range basis this_product while verdict spread is "prior".
- Cause: two ladders. range.ts needs >=3 shops within 90 days and takes quartiles (MIN_OWN_SHOPS=3, WINDOW_DAYS=90); estimate.ts takes 1+ shops up to 730 days, blended with category (A5). catalogue-first.ts shinRangeStands can show a range whose basis differs from the verdict basis.

##### B2. Range says "low confidence" and "no range reason", verdict says medium. CONFIRMED-LIVE (Oreo, both scans)
- Same response: `range.confidence "low"`, `noRangeReason "pool_too_wide"`, while `verdict.confidence "medium"`. A screen can show the "too thin / not enough" line and a Medium-confidence verdict with a zone word at once. Cause: catalogue-first.ts range confidence and estimate.ts confidence are computed separately (estimate.ts 1434-1440 forces own_prices to at least medium).

##### B3. Zone word inside the shaded 8-in-10 band. CONFIRMED-CODE (arithmetic) and consistent with live data
- bad cut = centre x 1.2 lies inside p10..p90 whenever sigma >= ~0.142 (1.2816 x sigma >= ln 1.2); same for the good and great cuts. Shopper price inside "Shaded: Pexi's estimate of 8 in 10 prices, X to Y" (ui-strings vd_band) but headline "Bad price". Live: Kraft PB $9.00 would be inside the $4.81 to $11.85 band and past the $9.06 bad line; milk and Kraft Dinner bands contain their own zone lines. Worst where p10/p90 are the AI's own low/high (estimate.ts 1339-1344) and priors (sigma up to EMPTY_PRIOR 1.0).

##### B4. Dots list does not match the centre. CONFIRMED-LIVE for duplicates, CONFIRMED-CODE for the rest
- Live: coconut milk lists "$1.75 Loblaws" and "$2.27 Walmart" twice (rows 1 and 11, 2 and 12: same shop, same price, 12 dots from 7 shops with duplicates). Kraft PB lists "$5.97 No Frills" sale twice (dates 11-08 and 11-07).
- Code: estimate.ts 1453-1463 builds dots from `ownAll` (all own rows up to 730 days, other-region rows, >5x "wrong row" outliers excluded from the centre, several rows per shop, rows older than the 90-day fresh window) while centre and n use `ownShops` (latest per fresh shop, regional, plausible). The "Prices Pexi has seen" list can show outliers and other-province prices, untagged, beside a centre that ignored them. Provenance "newest X days ago" (camera.js 1672) comes from all regular dots, possibly from a shop not in the centre.

##### B5. Fresh-window collapse: sibling of "7 from 7". CONFIRMED-CODE
- If any shop is within 90 days, `ownShops = fresh` only (estimate.ts 1124), so n can be 1 while 10 older rows are listed: provenanceLine (camera.js ~1658-1675) reads "10 prices from 1 shop" with "Few prices behind this" and Medium/"Fairly sure". Live Oreo is the mild form: 2 dots, n=1 (same shop twice).
- Going-rate card "Based on N sellers" (camera.js 1826) uses v.n = shops keyed seller|place, so N stores of one chain read as N sellers. SUSPECTED, low.

##### B6. The thin-evidence reason line is dead code. CONFIRMED-CODE
- `vd_why_own_count` ("1 price found, blended with its category") fires only when confidence is low and basis own_prices (camera.js 1628-1633), but own_prices is never low (estimate.ts 1434-1440). The true thin case (1 shop, medium) gets only the generic provenance plus the few_prices note, and that note is dropped when confidence is low (camera.js 1803).

##### B7. Rounded centre vs recorded scan. SUSPECTED, low
- Client recomputes zone and offByPct from the rounded centre (asShown / roundEstimateCents: nearest 5c under $10, 10c under $100, $1 above; shopperOf overrides the server zone), so a boundary price can show a different word from the one the server stored in the scan row (verdictRecord). Amount-mode lines are converted to percent of the exact centre server-side (estimate.ts 818-823) then applied to the rounded centre client-side. Centre under 3c throws in checkVerdict.

##### B8. Threshold edge cases. SUSPECTED
- zoneOf checks great first, so a user line with great <= good makes "good" unreachable (UI rangePatch prevents it; server accepts any). Server `direct` thresholds accept badPct up to 1000 and the client cleanThresholds accepts any >=0. Settled by api.js/scan-body.js: the user's lines ARE sent on every request when set (thresholdsFrom), and the live probes carry `fromShopper:false` defaults 30/20/20; a price typed after a priceless answer is judged client-side against base.thresholds (verdict-chart.js 286-306).

##### B9. Range sheet places a zone on estimate bases with flat lines. SUSPECTED
- catalogue-range.js placeShelf (86-106) uses the arithmetic midpoint for AI ranges, flat lines with no categoryOnly widening and no confidence softening, and places category_prior, department_prior and national_average with a zone word. Used only when the verdict is null (rare).
