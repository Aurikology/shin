# What is not ready for beta, against Jamin's walkthrough notes (2026-09-19)

Checked against the CODE (not plan docs) by two read-only audits on 2026-09-19. Requirements:
`docs/walkthrough/jamin-notes-2026-09-17.md` (his words, verbatim) and the "Walkthrough rulings"
section of `docs/jamin-gemini-rules.md`. File:line citations are the audits'; not every line was
re-verified by hand. Saved at his word: *"save this as a list"*, then *"include in the list the
constraints and rules for building and the intentions behind each item"*.

Each item: **Why** (his intention, his words where he gave them), **Build rules** (the constraints
the build must hold, from his rules unless marked suggested), **Now** (what the code does today).

## Rules for building any item on this list

1. **His word outranks everything**, then the system working, then Gemini's terms. *"nothing
   should hold higher precedency than the words of the founder."* A newer word of his beats an
   older one; a conflict with his word is raised with him, never settled quietly.
2. **A rule never crashes the system.** *"Breaking the rule should never crash the system. No rule
   is ever more important than the correct functionality of our system."* Legal and terms issues
   are marked, never blocked (rule 5). No guard machinery built around a Gemini term he never
   prioritised.
3. **Always an answer.** An answer with a "not fully confident" mark beats no answer (rule 6).
4. **One Gemini call per scan** returning product, prices, reviews and the price math (rule 1).
   A split into two calls is his call to make, not the builder's.
5. **No Claude inside Shin.** *"Claude should currently not be used anywhere inside shin."*
6. **The price does not come from Shin**, and Shin never shows price math it computed itself.
7. **Record everything** the user does and every Gemini request and answer (rule 4). Anything not
   recorded is a defect in the data collection system.
8. **Global, all languages.** Nothing Canada-only in new code.
9. **The Gemini API key is for live phone testing only**, never for building code (rule 8); use
   Claude in Chrome on gemini.google.com when building.
10. **Default model Gemini 2.5, and the beta tests 2.5 and a 3.x model side by side.**
11. **His examples are not the whole problem.** *"when i state a problem and give examples, don't
    assume those examples are the only aspects of the problem."*
12. **Standing repo rules still hold:** no savings claim until measured (CLAUDE.md hard rule 2),
    no public name until cleared (hard rule 1), aggression at the price or store never the user
    (hard rule 3), named paths in commits, trunk only, pull before and push after, tests green.
13. **Known conflict to clean up:** CLAUDE.md priority 1 says *"The good/fair/high call is
    arithmetic, never asked of a model."* His newer rule has Gemini do the math and Shin only check
    it in the background. His newer word wins; that CLAUDE.md line is stale.

## Blockers: the scan path contradicts his rules

**1. Photo identification runs on Claude.**
- Why: *"Claude should currently not be used anywhere inside shin."* With Gemini on, no Claude
  fallback (rule 7).
- Build rules: Gemini is the only provider on every scan path; remove the Claude default rather
  than hide it behind a setting; no fallback to Claude on a Gemini failure (mark and answer).
- Now: `model.ts:854-864` defaults to AnthropicProvider unless `SHIN_MODEL_PROVIDER=gemini`,
  which is unset; `server.ts:946`, `identify.ts:190`.

**2. Shin's own catalogue answers first; Gemini only on a miss.**
- Why: *"The server will not check shins own product list for now. The only thing the server will
  do is call gemini."* The catalogue *"will not be in use until more user data comes in."*
- Build rules: the server's scan path is one Gemini call; the catalogue stays in the repo and is
  fed by user scans (item 15), but is not consulted for the answer.
- Now: `server.ts:1321` photoLookup, `identify.ts:158-166`, `server.ts:2121`.

**3. Shin runs the price math locally and shows it.**
- Why: *"Shin should never run the price math iteself and output it to the user."* Also *"Shin
  will not run its own pricing system."*
- Build rules: the median, the placement of each price and the verdict against the user's
  thresholds come back inside the one Gemini answer (add them to `scan_prompt.md` and
  `response_schema.json` in `Shin_Gemini_Pricing_Engine/`). Shin's own math runs only as the
  hidden check in item 14.
- Now: `gauge.ts:622` computeGauge after `gemini-grounded.ts:434-441`.

**4. No Gemini 2.5, and no way to run both models in the beta.**
- Why: *"lets make the default gemini 2.5 for now and we will switch to a better model if our
  testing says otherwise."* *"both models should be tested for the beta."* 2.5 bills search per
  prompt (1,500 free a day), 3.x per query.
- Build rules: `gemini-2.5-flash` is the default; the server holds both model ids; each scan
  records which model answered; a report compares them on right product, searches, tokens, cost,
  seconds, and answers that did not parse. Any cost figure bills 2.5 per prompt.
- Now: defaults are `gemini-3.5-flash-lite` / `gemini-3.8-flash`
  (`identify/src/providers/gemini.ts:141-146`); only the offline matrix `eval/run.ts:87-161`.

**5. The answer format only works on Gemini 3, and a bad answer can fail the scan.**
- Why: rule 6 (always an answer) and his 2.5 default; Google allows a response schema together
  with search *"only to Gemini 3 series models."*
- Build rules: on 2.5, ask for the JSON in the prompt text and parse it; repair what can be
  repaired, mark what cannot, and still show an answer. Search tool name is `google_search`.
- Now: schema sent with `google_search` (`gemini-grounded.ts:438,441`); `parseJson` repair exists
  (`565-586`) but throws ProviderError (`604,700-701`).

**6. The user's good/bad/great thresholds never reach Gemini.**
- Why: *"These thresholds are crucial and non negotiable as not having them breaks gemini's rule
  of not being able to interpret geminis results."* The verdict must be on the user's own scale.
- Build rules: thresholds and shelf price go in every scan's context to Gemini. Suggested, not his: a user
  with no thresholds set gets the default range, never a scan without one.
- Now: stored (`setup.js:147`, `you.js:539`, `store.js:46-47`), never sent in `api.js`;
  boundaries come from the server (`price-line.js:331-332`).

## Barcode and camera

**7. Barcodes are not read until the button is pressed.**
- Why: *"The barcode should be automatically read out of every single frame. However, it does not
  automatically pop up the results."* *"The app should keep watching until the user presses scan
  barcode. The frames should act like a shift register, the user might point it at a barcode and
  decide they want to point it at another instead."*
- Build rules: decode every frame, always; the "Scan barcode" button appears only once a majority
  of frames over 1 to 2 seconds agree (not all frames will); the window slides, so pointing at a
  new barcode moves the focus; pressing sends the digits only, never the image; results never pop
  up on their own.
- Now: `app/src/eye/camera.ts:362` gates decode on `#barcodeWanted` (default false), one-shot
  (`camera.ts:367`, `barcode.ts:238`); button always rendered (`camera.js:2087`). The vote and
  window logic exists (`barcode.ts:112-113,215,229-231,259`; window 900 ms).

**8. Only the largest barcode is highlighted.**
- Why: *"The barcodes that can be identified on screen should all be highlighted in the prview as
  a guide for the user."* The focused one *"should be displayed differently so the user can
  differentiate."*
- Build rules: track and draw every barcode in view; the one the button will send has its own
  look; the focus follows the vote in item 7.
- Now: `barcode.ts:222-224` keeps one box.

**9. No "centre it" coaching.**
- Why: *"If the camera identifies a barcode, there should be prompts on screen that tell the user
  how to center the camera better."*
- Build rules: coaching appears while a barcode is seen but not yet confirmed (suggested, not his:
  it disappears once the button shows). Voice per the mascot copy rules; aimed at the framing, never the user.
- Now: `framing.ts:62,133` has hold, glare, closer, pick.

**10. The shelf price is asked after identification.**
- Why: *"asking the user for the price as soon as they scan instead of waiting for a product
  identificaiton first. This way, the price can get sent to gemini along with the rest of the
  prompt."* (He wrote "we can consider"; the one-call rule depends on it.)
- Build rules: price pad opens at scan time; the price rides in the one Gemini call; skipping the
  price still gets an answer (rule 6).
- Now: `camera.js:3450,3493,3255-3272`.

**11. The torch is a manual toggle.**
- Why: *"This should be a setting the user can do."* Auto-on at a brightness set by a slider that
  starts at Shin's default, or off with on-screen prompts when it is too dark.
- Build rules: a setting with both modes; the slider's starting point is Shin's current default
  threshold; the too-dark prompt only in the off mode.
- Now: manual toggle (`camera.js:2655,3792`), no darkness detection.

## Recording

**12. Gemini requests and answers are not stored whole.**
- Why: rule 4, *"we will record EVERYTHING"*; and so a wrong answer can be traced to the exact
  prompt (item 14).
- Build rules: every Gemini request and response is saved in full, linked to the scan and the
  model that answered. The grounded-results terms are a mark, not a block (rule 5).
- Now: `server.ts:2321-2341` keeps a derived summary.

**13. Photos only with consent; the user's rating keeps only the latest.**
- Why: *"Shin should try to save as much data as possible: The users' picture or barcode, the
  users' inputted price, the location, the store, whether it was a good deal."* The user's verdict
  is their interpretation, so it is theirs to keep, and it later back-computes a median.
- Build rules: save every rating, not just the last; photo capture is covered by the consent
  wording he delegated (*"you decide"*); suggested, not his: word it so the default is to save.
- Now: `scans.ts:317` consent-gated photo; `ratings.ts:91-102` latest only.

**14. No hidden check of Gemini's math.**
- Why: *"shin can run a confirmation check that does not get shown to the user. If gemini's
  calculations are wrong, the specific scenario... along with the prompt that was sent to gemini
  gets marked so we can access it later."*
- Build rules: never displayed (suggested, not his: recompute after the answer is shown, so it
  adds no wait); a mismatch marks the scan with its image or digits and the exact prompt.
- Now: nothing compares or marks (`gemini-grounded.ts:445-457`).

**15. Unknown products are never added to the catalogue.**
- Why: user data builds the catalogue: a match attaches to the product (the closest quantity when
  two sizes exist); a new product becomes a new entry; near-duplicates are grouped; the same
  product is kept per store type (his "branches"). *"All data from users should naturally be taken
  with a grain of salt."*
- Build rules: auto-create on a miss, marked as user-sourced and untrusted; convert to Shin's
  comparison units and keep the original; tech compared by model and spec, not weight; no Canada
  assumption.
- Now: misses logged for human review (`gaps.ts:38-50`).

**16. No continuous shelf capture.**
- Why: *"Cropped photos of what the camera sees can be constantly sent to the server to be saved.
  Espeically on store shelves, the product tag will contain the price of the item, the name of the
  item, and in the same photo frame, the item will also be there. This is very valuable data."*
- Build rules: never slows the viewfinder or the scan; no Gemini call per crop (storage only);
  covered by the consent wording. Suggested, not his: measure battery and data use on a real phone
  before the beta.
- Now: one frame per press, focused item only (`server.ts:1892-1903`, `camera.ts:545`).

## Features

**17. Onboarding: 2 of 33 screens exist.**
- Why: *"its cal ai's welcome pages which i added edits to for each page to make it fit for shin.
  Shin should use these pages but built with shin's design language."* Also *"there should be
  screens that collect user data: ask them where and what they typically shop for, ask them to
  determine their good, bad, and great price ranges, ask them for their location info."*
- Build rules: his text per screen, in his order, in Shin's own look (not Cal AI's). Every answer
  is saved (item 13). Decided 2026-09-18: the "10,000 shoppers", 4.8 rating, reviews and savings
  figures show real numbers only and stay hidden until they exist (also CLAUDE.md hard rule 2).
  Paywall prices ($39.99 a year, $12.99 a month) are his text.
- Now: only `setup` (thresholds) and `consent` (`main.js:36-49`); no shop, frequency, priority,
  chart, paywall, sign-in or setup screens.

**18. Alternatives have no modes and no constraints.**
- Why: Shin *"should also find competitive alternatives"*: non-organic for organic, used for new,
  the newer model for more. Two scenarios: validation (*"a farm product comparison might be
  useful"*) and switching (*"they would definitly not accept a farm alternative if they are buying
  in a supermarket"*). *"There needs to be constraints in place for things like buying things in
  massive bulk."*
- Build rules: alternatives come from the one Gemini call (rule 3, not Shin's catalogue); the two
  modes are distinct; bulk, farm vs store, and used vs new are constraints, and his examples are
  not the full list (rule 11); a user buying from a farm may take a supermarket option.
- Now: one path (`catalogue/src/alternatives.ts:630`).

**19. Canada still hardcoded.**
- Why: *"Shin will be available to the entire world and not focused on canada."* Same-country
  prices compare; across countries they do not, with exceptions (provinces that differ, EU
  countries that match); *"will need further deisgn"*.
- Build rules: market and currency come from the user's location; never convert currencies; the
  cross-country comparability rules go to Gemini in the prompt.
- Now: `alternatives.ts:559,591` `sold_in_canada=1`; `spine.ts:664+` CAD text; `gauge.ts:222`.

**20. kg and l conversion wrong in alternatives.**
- Why: *"items should not be matched based on quantity and should be converted to the units of
  comparison used in this app. However, the original units should alos be stored."*
- Build rules: one conversion used everywhere (the verdict's is correct); keep the original.
- Now: `alternatives.ts:273-276,696` (the verdict's `verdict.ts:175-192` is right).

**21. Offline mode still identifies barcodes.**
- Why: *"For now, the app will not be usable offline."*
- Build rules: with no network the app says so and does not answer from local data.
- Now: `app/public/js/offline-aisle.js:48-66,81-83`.
