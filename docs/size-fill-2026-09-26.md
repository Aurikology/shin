## Two bugs found in the shared parser, fixed for every caller

Both found by running the filler against the real catalogue, not anticipated in advance, and both
fixed in `catalogue/src/units.ts`'s `parseQuantity` — the one parser every caller (this filler,
`alternatives.ts`, `search.ts`) shares — with regression tests:

1. **A leading-dot decimal with no leading zero was misread as the whole number.** ".6kg" matched
   on the bare "6", turning 0.6 kg into 6 kg — real row, barcode `0055742564136`, name "small
   breed compliments .6kg". Fixed: the value group now also accepts `\.\d+`.
2. **A zero multiplier was silently dropped instead of rejected.** `pack ? pack * each : each`
   treated "0 x 88 ml" the same as no multiplier at all (0 is falsy in JS) and returned 88 ml —
   real row, barcode `0059749981095` name "Crunchy almond", quantity "0 x 88 ml". Fixed: a
   multiplier of 0 or less now returns null.

A third guard is local to the name path only (`size-fill.ts`, not `units.ts`, because it is about
what a *name* can mean, not about parsing): a milligram figure in a name is a supplement's
per-capsule dose, never a package weight — real rows "L-lysine 1000 Mg" and "Caffeine 200 Mg" —
and a name-derived size over 50 kg / 50 L is a misprint or lot count, mirroring the cap
`prepare_rows.py`'s `size_from_name` already applies at load time — real row "ME BOUCHÉE
FRAMBOISE 240KG" (not a 240 kg raspberry bite).

## The falsifier: did it fire?

**No**, on the only mechanical cross-check that applies (below), and no wrong sizes found in a
hand-check of all 126 quantity-sourced fills plus all 19 name-sourced fills — the full set, not a
sample, since the total was small enough to check completely.

**Mechanical cross-check** (quantity-sourced fill vs. what the name itself says): of the 126
quantity-sourced fills, **zero** have a name that also prints an independently checkable size —
product names in this bucket are almost entirely "Large Eggs", "Brown Eggs", etc. with no size
printed at all, so the plan's own falsifier test (compare the gained size against what the name
says) has no data to disagree on for this bucket. That is reported as "not measurable here," not
as a pass.

**Hand check, all 145, read one by one**: no size disagreed with its source string. One case is
worth flagging rather than calling clean: barcode `0055742564136`, "small breed compliments
.6kg", has an empty category and reads like a dog-food product name ("Compliments Small Breed" is
a real Canadian pet-food line) that OpenFoodFacts' own crowdsourced data has filed under regular
food. It is not this unit's job to re-curate OpenFoodFacts' own categorization — the predicate
this filler and the rest of the codebase already use for "Canadian food and drink" is
`source = 'openfoodfacts'`, and this row passes it — but the size itself (0.6 kg) is read
correctly off the string that is actually there, whatever the product turns out to be.

## Which rows this filler touches, and whether any are not food

Every row is `sold_in_canada = 1 AND source = 'openfoodfacts'` — the codebase's own definition of
"Canadian food and drink" (`export-pack.ts`'s grocery-pack predicate). No electronics, beauty, pet
food, or other-source row is touched; the model-number and non-food hard cases above were checked
so this filler is proven never to misfire on that shape, not because it can reach one. The one
caveat is the row named above: OpenFoodFacts' own crowdsourced data appears to have filed at least
one pet-food product under this source, which is a pre-existing data-quality issue in the upstream
feed, not something the size fill introduced or can safely fix by inference.

## What was found and not fixed

Of the 96,088 no-size rows, only 1,025 carry any `quantity` text at all; of those, 899 fail to
parse. The large majority of the 899 are bare numbers with no unit word at all ("50", "1", "450",
"1/2") — genuinely unknowable, correctly left null. A small remainder (roughly 1-2%, e.g. "6
Tablets", "10 bags", "1 can", "6 sachets de 2 gâteaux") use count nouns `units.ts` does not carry.
Not extended: too rare to be "a shape that appears often," and the multi-item ones ("6 sachets of
2 cookies") are second-order ambiguous — is the size 6 or 12? — exactly the kind of guess this
unit is built to refuse. Name extraction found only 19 unambiguous, end-anchored sizes across
96,088 names; most Canadian OpenFoodFacts names in this remaining pool simply do not print a size
anywhere in the name either.
