Build order / for the walkthrough dated 2026-09-03

The correcting build

A build order for the price scanner, sequenced by what cannot be taken back, with the mechanism that makes it catch its own errors written into the structure rather than asked for at the end.

The one thing this plan is organised around A plan cannot improve itself. A build improves when evidence about its mistakes is produced by something that did not make them. Which is why almost none of this document is about code review. Agents are good at code review. The thing that will be wrong, and the thing a user can catch in ten seconds, is the price on the screen. That is what gets a permanent instrument pointed at it.

What this builds, and what it leaves alone

The walkthrough lists roughly sixty feature options. That is a menu. This is the order of operations for the floor underneath it.

The walkthrough's narrowed floor is one category, barcode and screenshot input, three faces, save and watch, a still share card, and the disagreement branch. Live photo recognition is out. Every other option in that document becomes the backlog, and the accuracy scoreboard built in phase three is what ranks it, rather than taste.

One thing in the walkthrough changed shape after it was tested and the plan inherits the new version: there is no single verdict screen. Each category needs its own sentence, because the comparison that makes it true is different. Grocery compares this week's promotion to the regular price. Tech compares retailers. Used goods compare live asking prices. Furniture compares the item to its own history, because nobody else sells it. Building one screen and parameterising it later is the mistake this paragraph exists to prevent.

Phase order

Ordered by what is spent once, not by what is easy or interesting. A form gets refilled in minutes; a store listing, a trademark and a first video do not.

00days

The two things no agent can do for you

No code. Both can redirect everything downstream, and both are cheap.

Founder only

The trademark search. Twenty minutes at CIPO against Nongshim's marks in the software classes. It gates the store listing, and a store listing is spent once. This is a legal risk judgment about a name you will live with, so it is yours, not an agent's.

The two-caption video test, through borrowed audiences. Three to five micro creators, or a subreddit where distribution is not follower-gated. Not a fresh handle: new posts seed to existing followers first, so a cold account can return near zero views and hand you a false negative on the one test everything else is sequenced behind. Run your own handle alongside it only to start building the seed.

Gate out of phase 00

A category and a caption chosen because something outperformed, plus a name that survived a search. Nothing downstream starts on a preference.

011 to 2 wks

The price spine, alone, with no interface

One category. One agent. No parallelism, because there is nothing yet to be parallel to.

Single lane

Build only this: given a product identity, return a verdict object or refuse to. No camera, no mascot, no screens. The reason it goes first is that the pilot proved this is the fragile part, and the reason it goes alone is that every other lane consumes its output shape. Fixing that shape after four lanes have built against it is the expensive version of this mistake.

The verdict object carries the comparison set it used, the count of points in it, the date of each, and the sentence type for the category. If it cannot produce those, it refuses. A refusal is a supported outcome here, not an error, and phase three measures how often it happens.

Acceptance, and it is not a passing test suite

One hundred items in the chosen category, run through it. Then a fresh agent that never saw the code takes twenty of those verdicts, goes and finds the real prices, and scores them. That number is the acceptance, not the test suite.

Written before the build, so it can actually fire

The pilot produced a usable range for 2 of 7 items from free search. A paid feed that does not clear that comfortably is not worth buying, and a category whose feed cannot clear it is the wrong category. If that happens, phase 00's answer gets rerun with the next category, not patched with heuristics. The floor is derived from the pilot; the number you would actually defend in public is yours to set, and it should be set now rather than after you have seen the result.

022 to 3 wks

Four lanes, once the shape cannot move

Genuinely independent work in separate worktrees, each with its own brief, branch and deny list.

Parallel, conductor above

Lanes are only lanes if they do not read and write the same things. These four qualify because phase 01 fixed the contract between them.

Gate out of phase 02

Four branches merged by the conductor, each against its own written acceptance, plus one thing that does not come from any lane: twenty verdicts checked by hand in a real store on one shopping trip. That is an hour of your time and it is the only check in this plan that no agent can fake.

03permanent

The loop, which starts before launch and never stops

This is the part the request was actually about, so it is specified rather than described.

Runs weekly, forever

Four mechanisms. Each exists because the version without it has a named failure mode, and two of those failures happened while the walkthrough was being written.

Every task carries its falsifier, written before the build

Not "does it work" but "what observation would prove this wrong." Written into the brief, before any code, by whoever writes the brief. The failure mode without it: the walkthrough labelled its own central claim untested three times in three sections and shipped the label instead of the test. The test took seven searches and reversed two decisions in the document that was flagging it.

The thing that checks never shares context with the thing that built

A fresh process, no project instructions loaded, given only the brief's acceptance test and the diff. This is not a formality: on a prior spec in another project this pattern caught five blockers, two of which the spec itself had created. An author reviewing their own work is the weakest form of review available, and it is the default that has to be designed out.

One adversary whose only job is to produce a wrong verdict

It writes nothing. It hunts for items where the app says "ripped off" and the price is fine, or says "steal" on a counterfeit. It reports what it found and how it found it. Price is verifiable and consequential, which is what separates this app from the calorie scanners it is modelled on: a wrong calorie count costs the user nothing they notice, and a wrong price gets argued with by a seller standing in front of them.

A correction becomes a standing rule only after the same defect is logged twice

Once is a bug fix. Twice is a missing rule. This exists because the alternative was measured in this repo: twenty-eight standing instructions written in twenty-two days, fifty-eight of the resulting rules with neither a quote nor an incident behind them. A self-improving plan with no bar for entry becomes a rulebook nobody reads, which is a worse outcome than no loop at all.

The defect log is one table and its only interesting column is the last one

Date, what was wrong, what the user saw, which lane, and whether a test caught it or a human did. A defect caught by a human is a missing test, and the fix is the test rather than the bug. If that column fills up with humans, the loop is not running, whatever else the plan says.

The scoreboard is one tracked number with a date on it

A fresh agent, weekly, pulls a random sample of logged verdicts, goes and finds the real prices, and scores them. Accuracy is a series from week one rather than an audit before launch. Three other numbers get instrumented on day one because no benchmark can supply them and they decide the business: scans per user per week split by whether a purchase followed, watch rate as the share of scans that end in a save, and distinct products over total scans, which decides whether caching rescues the per-scan cost.

Who does what, and at what tier

Every multi-lane launch gets a conductor above it. The conductor reviews and merges and never writes a line, because a reviewer who wrote the code is not a reviewer.

Two tier rules that are not preferences. Workers run mid tier, never the top one: a four-lane launch at top tier was measured here as a large and pointless cost, and the reasoning that justified it did not survive contact. The top tier manages and does not build, in any surface. Reserve it for the conductor and for interactive work.

What no agent in this plan can do

Naming these is the difference between a plan and a wish.

  • The video test. It needs a real audience. Agents can draft the two captions and cannot make anyone watch them.
  • The store submission. Spent once, and it is yours. Everything up to the submit button is the system's to prepare, including the listing copy and the assets.
  • Standing in a store with a phone, checking twenty verdicts against the shelf. One trip, one hour, and it is the only check here that cannot be faked by something that wants to report success.
  • Deciding the name. Trademark exposure is a risk you carry, not a search result.

Machinery, verified rather than assumed

This repo already has the lane launcher. Four things about it were checked rather than recalled.

  • It takes a repository path as a parameter, so it can drive a separate app repository instead of this one.
  • Its remote check permits exactly one remote, named origin, pointing at private GitHub, and refuses anything else. That is what the app repository should have, so the check passes rather than blocks.
  • Launching it from inside a session needs the flag that stops it inheriting the wrong terminal, or it spawns a silent orphan. A dry run first costs nothing and catches missing briefs and path collisions.
  • A spawn is not a start. The launcher's own transcript check is what tells you a lane is alive, and past roughly four live lanes it warns for a reason.

What would prove this plan wrong

Three weeks in, if the accuracy scoreboard is flat or absent, the loop is decoration and the central claim of this document failed. The second signal is the defect log's last column: if humans are finding the defects, the tests are not, and no amount of process written on top of that changes it.

The honest read on the plan's own confidence: phases 00 and 01 rest on a measurement taken by hand. Phase 02's lane split rests on the contract from phase 01 holding, which is an assumption until it does. Phase 03 rests on the four mechanisms being run when nobody is watching, and that has never been true of any process document written in this repo, which is the reason the twice-before-a-rule bar is in it.
