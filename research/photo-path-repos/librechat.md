## Q4 when and how hard it searches
- **Toggle, not a dial.** `web_search` is a plain boolean pulled off `options.modelOptions` and pushed as an empty-object tool: `packages/api/src/endpoints/google/llm.ts:722-724` `if (enableWebSearch) { tools.push({ googleSearch: {} }); }`. No second argument, no config object, nothing numeric goes into that push. This is the entire mechanism that decides whether Gemini can search at all; there is no per-call decision about "how often."
- **User-facing config confirms it's boolean-only.** `packages/data-provider/src/parameterSettings.ts:815-826`: the `google.web_search` setting is `type: 'boolean'`, `component: 'switch'`, `default: false`, labeled `com_endpoint_use_search_grounding`. No `type: 'number'`/`slider` field exists next to it for Google anywhere in this file.
- **Zod schema confirms the field doesn't exist even server-side.** `packages/data-provider/src/schemas.ts:1449-1470` `googleBaseSchema` picks a fixed field list from `tConversationSchema` (`web_search: true, url_context: true, thinking: true, thinkingBudget: true, thinkingLevel: true, ...`); there is no `dynamicThreshold`/`searchThreshold`/`groundingThreshold`/similar key in the pick list. `GoogleParameters` (`packages/api/src/types/google.ts:4`) is `z.infer<typeof googleBaseSchema>`, so the TypeScript type used everywhere else in the Google client-options builder also has no such field.
- **Repo-wide grep is empty.** `grep -rn "dynamicThreshold|dynamic_retrieval|DynamicRetrievalConfig|MODE_DYNAMIC" --include=*.ts --include=*.js .` (excluding node_modules, which doesn't exist in this clone) returns zero hits anywhere in the repository, including tests, YAML, and docs. **The claim is false: this repo has no threshold field at all, not even a hardcoded or dead one.** There is nothing to report a default/range/meaning for because the field does not exist in this codebase.
- Why it matters for Shin: a "search only when confidence is low" control is exactly what Shin needs to stop searching unconditionally on every scan; LibreChat cannot be copied for that behavior because it never implemented per-call search gating for Gemini, only a session-level on/off switch a human sets once in settings.

### Dynamic retrieval threshold
- Does not exist in this repo. No `default`, `range`, or `meaning` to report; not user-exposed because there is nothing to expose.

### googleSearchRetrieval vs googleSearch
- Only `googleSearch: {}` is ever constructed, at `packages/api/src/endpoints/google/llm.ts:723`. `googleSearchRetrieval` appears in exactly one place in the whole repo as a *detection* string, not a builder: `packages/api/src/agents/initialize.ts:365` `return 'googleSearch' in tool || 'googleSearchRetrieval' in tool;` inside `hasGoogleSearchTool`, used only to recognize an already-built tool object so it can be filtered/stripped later (e.g. by role denial). Nothing in this repo ever sets the `googleSearchRetrieval` key on a tool object.
- **No model-version switch exists.** There is no `if (model.startsWith('gemini-1.5'))` or equivalent branch anywhere; the single `tools.push({ googleSearch: {} })` call is unconditional on model version (only conditional on the `enableWebSearch` boolean). The `googleSearchRetrieval` string is legacy-compatibility detection code for a shape this repo's own code never produces.

### Forcing or forbidding search
- No `tool_choice`/`mode: ANY|AUTO|NONE` construct for Google's search tool anywhere in `llm.ts` or `initialize.ts`; the only control is the on/off `web_search` boolean plus a model-compatibility gate (see below) that can force the tool combination to fail outright rather than choose search frequency.
- **Model-version gate exists, but for a different problem: combining Google's native tool with other agent tools, not search frequency.** `packages/api/src/agents/initialize.ts:184-192` defines an allowlist (`gemini-3-flash-preview`, `gemini-3-pro-preview`, `gemini-3.1-flash-lite`, `gemini-3.1-pro-preview`) plus a `isGemini35OrLater` version check (`initialize.ts:495-503`, regex `^gemini-(\d+)(?:\.(\d+))?(?:-|$)`), and excludes any model id matching `-image-`, `-live-`, `-tts-` (`initialize.ts:191-192`). `assertGoogleToolCombinationSupport` (`initialize.ts:533-536`) throws `{"type":"google_tool_conflict"}` when `hasProviderTools && hasAgentTools` (i.e. `googleSearch` plus any function-calling/MCP tool) on an unsupported model. Test proof: `packages/api/src/agents/__tests__/initialize.test.ts:1210-1220` shows `gemini-2.5-flash` (and `gemini-3-pro-image-preview`, `gemini-3.5-flash-live`, `gemini-4-pro-tts`) **rejects** the combination (`rejects.toThrow(/google_tool_conflict/)`), while `initialize.test.ts:1140-1150` shows `gemini-3.5-flash`, `gemini-3.1-pro-preview`, etc. allow it.
- Why it matters: this is a real, tested model-version gate in Google's own SDK usage, but it gates "can I combine googleSearch with my own function tools", a capacity/compatibility check, not a "search less often" throttle. Shin's problem (searching unconditionally every scan) has no analog here.

### Cost/call control
- **Generic recursion cap, not search-specific.** `packages/api/src/agents/config.ts:4` `const DEFAULT_RECURSION_LIMIT = 50;`, resolved per-run by `resolveRecursionLimit` (`config.ts:19-35`) via YAML default -> per-agent override -> YAML max cap. This caps total LangGraph steps for the whole agentic turn (any tool, not just search) and is the only "budget ending a loop" mechanism found.
- Nothing counts Gemini search calls specifically, nothing caches/reuses a prior search result, and nothing reports what is returned when the recursion budget is hit versus a search-specific limit. Grep for `groundingMetadata|grounding_metadata|searchEntryPoint|groundingChunks|groundingSupports` across the repo (excluding node_modules) returns zero hits, so grounding metadata is not even read back from the response, let alone counted.

## Q1 image plus search
- **Yes, on the agents path, nothing blocks image + googleSearch on the same call.** Images are attached via `addImageURLs` (`api/server/controllers/agents/client.js:2046-2061`), which calls `encodeAndFormat(...VisionModes.agents)`; for that mode the image becomes `{ type: ContentTypes.IMAGE_URL, image_url: { url, detail } }` where `url = data:${file.type};base64,${imageContent}` (`packages/api/src/files/encode/image.ts:199-201`), i.e. an inline base64 data URL attached to the message, not a separate call. Separately, `getGoogleConfig` in `llm.ts:722-724` builds `tools: [{ googleSearch: {} }]` on the same agent's `llmConfig` whenever `web_search` is on. Both the per-agent `llmConfig`/tools and the per-turn `messages` (carrying the image content) are handed to the SAME `createRun({ agents, messages, ... })` call: `api/server/controllers/agents/client.js:4902-4908` (`agents` and `messages` are sibling fields of one call). Nothing in `initialize.ts`'s tool-combination gate (`assertGoogleToolCombinationSupport`) inspects message content or image presence, it only inspects `hasAgentTools` (other function/MCP tools), so an uploaded image never trips it.
- **Where the wire-level Gemini request is actually built (the base64 data URL becoming a `Part` with `inlineData`, and the tool array becoming the request's `tools` field) is not in this repo.** `createRun`, `Providers`, `GoogleClientOptions`, and the actual provider request/response classes are imported from `@librechat/agents` (`api/server/controllers/agents/client.js:4-5`, `packages/api/src/endpoints/google/llm.ts:1`). This clone has no `node_modules` directory at all (`find . -maxdepth 2 -iname node_modules` returns nothing), so `@librechat/agents` (`packages/api/package.json:123`, `^3.8.7`) and `@google/genai` (`packages/api/package.json:121`, `^2.8.0`) are npm dependencies only, not vendored as source anywhere in this clone. **Nothing here on the actual HTTP request body construction from Part/tools to the Gemini API, lives in `@librechat/agents` / `@google/genai`, not vendored in this repo.**
- Model id / SDK version: model id is whatever `agent.model` resolves to (e.g. `gemini-3.5-flash` in the tests); SDK versions are `@librechat/agents@^3.8.7` and `@google/genai@^2.8.0` per `packages/api/package.json:121,123`.
- Resolution/token hints: `detail` (image detail hint, e.g. low/high) is passed through `params.imageDetail` into `encodeAndFormat` and lands in `image_url: { url, detail }` (`image.ts:199-201`); no `media_resolution`, no image cropping/resizing code found in `image.ts` (only base64 validation via `validateImage`, `image.ts:186-196`). Thinking budget/level, temperature, and system instruction are separate `llmConfig` fields built earlier in `llm.ts` (thinking config at `llm.ts:520-557`) but are independent of whether an image or googleSearch is present; no code was found that changes temperature, thinking, or system instruction based on image+search co-occurrence.
- Why it matters for Shin: LibreChat's own architecture proves image content and the search tool routinely coexist on one Gemini call with zero special-casing, i.e. nothing here validates or invalidates whether combining a photographed item's image with a live search call is safe or effective; that question has to be answered against the actual `@librechat/agents` request builder, not this repo.
