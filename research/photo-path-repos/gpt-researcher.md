# assafelovic/gpt-researcher

One line: it is a multi-retriever web-research orchestrator that runs its own search API calls (Tavily by default, 15+ others swappable), scrapes the resulting pages itself, chunks and embeds the scraped text to filter it for relevance, then feeds the surviving text to an LLM with a prompt instruction to cite; nothing in the codebase verifies that a citation in the output actually matches the text it sits next to.

Read depth: opened gpt_researcher/actions/{query_processing,retriever,web_scraping,report_generation,markdown_processing}.py; gpt_researcher/context/{compression,retriever}.py; gpt_researcher/skills/{researcher,curator,context_manager,writer,deep_research}.py (deep_research.py read in full, researcher.py read in full via targeted offsets covering conduct_research, plan_research, _get_context_by_web_search, _process_sub_query, _combine_mcp_and_web_context, _search_relevant_source_urls, _scrape_data_by_urls, _get_new_urls); gpt_researcher/memory/embeddings.py; gpt_researcher/prompts.py (sections: generate_search_queries_prompt, generate_report_prompt, curate_sources, generate_resource_report_prompt, generate_subtopic_report_prompt); gpt_researcher/utils/{validators,llm,costs}.py; gpt_researcher/vector_store/vector_store.py; gpt_researcher/retrievers/base.py and retrievers/tavily/tavily_search.py; gpt_researcher/config/variables/default.py; gpt_researcher/scraper/scraper.py (page-quality reject logic only). ## QA query and reformulation

- The search string is generated by an LLM call, not a template. `generate_sub_queries` (gpt_researcher/actions/query_processing.py:83-156) builds a prompt via `prompt_family.generate_search_queries_prompt(...)` and sends it to `cfg.strategic_llm_model`. Exact prompt text, gpt_researcher/prompts.py:248-259 (`generate_search_queries_prompt`, staticmethod at prompts.py:213):
  `"Write {max_iterations} search queries to research the following task: \"{task}\"\n\nEach query must be a plain natural language phrase. Do not use search operator syntax such as site:, filetype:, inurl:, intitle:, OR, AND, or NOT — these operators are not universally supported and will return empty results on many search backends.\n\nAssume the current date is {datetime.now(...)} if required.\n\n{context_prompt}\nYou must respond with a list of strings in the following format: [{dynamic_example}].\nThe response should contain ONLY the list."`, NEEDS OUR OWN SEARCH (the mechanism issues queries against a search API), but the prompt-writing technique itself, asking a model to produce N plain-language query variants as JSON, with an explicit "no operator syntax" instruction, FITS as a pattern for a second Gemini call that reformulates the photo/price question before the grounded call.
- Reformulation on a weak/empty result: nothing rewrites the query and retries. Grepped for "retry", "reformulate", "rewrite" in gpt_researcher/actions/query_processing.py, gpt_researcher/skills/researcher.py, gpt_researcher/skills/deep_research.py. Found only: (a) LLM-call-level retry that repeats the identical prompt on exception/empty response (utils/llm.py:116-141, see QD), and (b) Tavily's own zero-result path, which raises an exception that is caught and turned into an empty list, not retried (retrievers/tavily/tavily_search.py:140-141, 153-155). In `_process_sub_query` (skills/researcher.py:624-632), an empty `combined_context` just logs `"No combined context found for sub-query"` and returns empty, no rewrite, no second attempt with a different query. Absence confirmed. FREE (this is what's missing, not present, labeled for completeness of the absence).
- Sub-question count: `max_iterations=cfg.max_iterations or 3` (actions/query_processing.py:113), default `"MAX_ITERATIONS": 3` (config/variables/default.py:25). This is a one-shot count of how many queries the LLM is asked to produce in a single JSON list, not an iterative loop counter. The original query is also appended after sub-query generation for non-subtopic reports (`sub_queries.append(query)`, skills/researcher.py:368), so up to 4 total queries run. All sub-queries are dispatched concurrently via `asyncio.gather(*[self._process_sub_query(sub_query, ...) for sub_query in sub_queries])` (skills/researcher.py:382-387) and merged by filtering falsy results then `" ".join(context)` (skills/researcher.py:390-392), NEEDS OUR OWN SEARCH.
- Query-level constraints: site restriction via `query_domains` → Tavily's `include_domains` param, plus a regex that rewrites Google-style `site:` operators the LLM sometimes emits into `include_domains` because "Tavily rejects them" (retrievers/tavily/tavily_search.py:14-15, 114-126). Recency: Tavily's `_search` signature default `days: int = 2` (tavily_search.py:70) but `search()` never passes `days` through to `_search` (tavily_search.py:128-134), so the recency window is dead/unused at the call site actually exercised, NEEDS OUR OWN SEARCH either way. No language/region setting found on the search call itself; `cfg.language` (default "english") is only used in report-writing prompts (prompts.py:314, 469), not in query construction, FREE/NEEDS OUR OWN SEARCH split noted, but nothing to report as a query-time language filter.

## QB source trust

- Similarity filtering uses `EmbeddingsFilter` from langchain with a cosine-similarity threshold. Default in the config surface actually wired to `ContextCompressor` is `SIMILARITY_THRESHOLD: 0.42` (config/variables/default.py:6), passed through `ContextManager.get_similar_content_by_query` → `similarity_threshold=getattr(self.researcher.cfg, "similarity_threshold", None)` (skills/context_manager.py:58). If that value is ever `None`, `ContextCompressor.__init__` falls back to `float(os.environ.get("SIMILARITY_THRESHOLD", 0.35))` (context/compression.py:122-124), two different defaults for the same knob depending on path (0.42 from config, 0.35 as the compressor's own env fallback). A separate, unrelated threshold of 0.5 is the default for matching previously-written report sections against new subtopics: `__get_similar_written_contents_by_query(..., similarity_threshold: float = 0.5, ...)` (skills/context_manager.py:125). Chunking before filtering: `RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=100)` (context/compression.py:134, repeated at 224 for written-content compression). `async_get_context` returns up to `max_results` chunks (default 5, called with 10 from context_manager.py:63). NEEDS OUR OWN SEARCH (this is an embedding index over scraped pages).
- A compression fast-path skips embeddings entirely when content is small: `if total_chars < chunk_threshold and len(self.documents) <= max_results` where `chunk_threshold = int(os.environ.get("COMPRESSION_THRESHOLD", "8000"))` (context/compression.py:163-167), below 8000 total characters across all scraped docs, it just formats the raw docs directly with no relevance filtering at all. FREE (pure length check, no model call) but worth flagging: under this path nothing scores relevance at all, not even embeddings.
- Deduplication is by URL, via a `visited_urls` set threaded through the whole research run: `_get_new_urls` only keeps a URL if `url not in self.researcher.visited_urls` (skills/researcher.py:810-813), and the set is deliberately not cleared between sub-researcher passes so subtopic reports don't re-scrape the same page (skills/researcher.py:108-111 comment). No content-hash dedup found anywhere (grepped researcher.py, web_scraping.py, vector_store.py). FREE.
- Page content is fetched and cleaned by a dedicated `Scraper` class (gpt_researcher/scraper/scraper.py), which is NEEDS OUR OWN SEARCH machinery end to end (it drives real HTTP fetches / headless browser). Before a scraped page is accepted as a source it runs local quality checks, all pure logic with no model call: rejects if `not content or len(content) < 100` ("Content too short or empty", scraper.py:232-233); rejects if `_looks_like_block_page(content)` ("Anti-bot/challenge page detected", scraper.py:242-243); rejects if `_looks_like_word_list(content)` (scraper.py:245-246); and retries once via `PyMuPDFScraper` if the content looks like unextracted PDF binary (scraper.py:248-257). A rejected page is turned into `{"url": link, "raw_content": None, ...}` and dropped downstream (scraper.py:276-281, `_reject`). Truncation: raw content fed into the embedding retriever is capped at `_MAX_CONTENT_CHARS = int(os.environ.get("MAX_CONTENT_CHARS", 50000))` chars (context/retriever.py:9-13, 29), explicitly to stay under OpenAI's embedding token cap. NEEDS OUR OWN SEARCH (all of this operates on scraped HTML/PDF bytes Shin's architecture never has).
- Domain/date/source-quality filtering exists only as a prompt instruction to the LLM, not as code. `filter_urls` (actions/web_scraping.py:54-76) only excludes domains named in `config.excluded_domains`, a literal denylist, no ranking. Actual "prefer trustworthy/recent sources" logic is delegated to the model: prompts.py:306-307 ("You MUST prioritize the relevance, reliability, and significance of the sources... prioritize new articles over older articles if the source can be trusted") and the optional curator step, `curate_sources` (skills/curator.py:35-111), which sends all scraped sources to `cfg.smart_llm_model` with the prompt at prompts.py:319-350 ("EVALUATION GUIDELINES: 1. Assess each source based on: Relevance... Credibility... Currency... Objectivity... Quantitative Value...") and asks it to return a re-ranked JSON list; on any parse failure it falls back to returning the original uncurated list unchanged (skills/curator.py:102-111). This curator is opt-in and off by default: `"CURATE_SOURCES": False` (config/variables/default.py:17). The evaluation itself (an LLM call judging source quality against stated criteria and returning a re-ranked/filtered list, with a code-level fallback on malformed output) FITS as a second-Gemini-call pattern; the fact that it operates over a set of independently-scraped pages is NEEDS OUR OWN SEARCH.
- Number/price/currency/date extraction from a page: hunted specifically. ## QC citation attachment

- **This is the deliverable question, and the answer is: citations are entirely a prompt instruction on free-text output; no code matches an answer sentence back to a source span.** The instruction, quoted verbatim, prompts.py:309-310 (`generate_report_prompt`, prompts.py:262): `"- Use in-text citation references in {report_format} format and make it with markdown hyperlink placed at the end of the sentence or paragraph that references them like this: ([in-text citation](url))."` and `"- Every substantive claim, figure or quote MUST carry an in-text citation to the source it came from. Do NOT cite sources that do not appear in the provided information."` The same instruction text (near-identical wording) recurs for the resource-report prompt (prompts.py:479), the subtopic-report prompt (prompts.py:664, 713), and the deep-research-hierarchy prompt (prompts.py:746). `generate_report` (actions/report_generation.py:209-326) sends this prompt plus the assembled context straight to `cfg.smart_llm_model` via `create_chat_completion` (report_generation.py:292-306) and returns whatever markdown text comes back, there is no post-processing step in that function, or anywhere found by grep for "citation"/"Citation" across gpt_researcher/, that parses the model's output and checks a cited URL against the source text near it. FITS as a prompt technique alone (a citation instruction is trivially portable to a Gemini call), but the labeling must be explicit: the model is *told* to cite; nothing verifies it did so correctly, or at all.
- Two code mechanisms attach source identity to content *before* the model writes, which is not the same as verifying citations *after*: (1) `_combine_mcp_and_web_context` appends a literal `f"\n\n*Source: {title} ({url})*"` string after each MCP content chunk before it enters the LLM's context (skills/researcher.py:759-764), this labels input, it does not check output. (2) `add_references(report_markdown, visited_urls)` (actions/markdown_processing.py:101-127) appends a `## References` section listing every URL in `visited_urls`, sorted for reproducibility (`"- [{url}]({url})\n" for url in sorted(visited_urls)`, markdown_processing.py:122), but this is not span-matched either: it dumps **every URL the scraper ever visited**, whether or not the model actually cited or used it in the final text. Also notably **not wired into the default report path**: `write_report()` (skills/writer.py:49-134, called from agent.py:451-480, used by backend/report_type/basic_report/basic_report.py:74) never calls `add_references`; the only call site found by grep is `backend/report_type/detailed_report/detailed_report.py:200`, appending it to the conclusion of the detailed-report flow specifically. FREE (pure string concatenation, no model call) but reported precisely: it is a blunt "list every visited URL" append, present in one report type only, not a citation-correctness check.
- A separate, code-level citation-extraction pattern exists in deep_research.py, but it parses citations the *model claims* in its own JSON/text output, not something matched against source content. `process_research_results` (skills/deep_research.py:346-378) prompts the LLM with a rigid schema, `'{"learnings": [{"insight": "<insight>", "sourceUrl": "<url or empty string>"}], "followUpQuestions": [...]}'` (deep_research.py:361-362), and the response is run through `parse_research_results_response` (deep_research.py:143-205), which pulls `item.get("sourceUrl") or item.get("citation")` into a `learning -> citation_url` dict (deep_research.py:156, 164), with a regex fallback `LEARNING_LINE_PATTERN`/`URL_PATTERN` (deep_research.py:41-45, 186-197) if the model didn't return clean JSON. This is a real piece of code that parses a model's self-reported citation into a structured field, with a fallback path when the model's output is malformed, FITS (a response-shape parser + fallback regex is directly portable to parsing a Gemini response for a claimed source-URL-per-fact, and is the closest thing in this repo to "code that touches citations" rather than just prompting for them). It still does not verify the `sourceUrl` is the page the fact actually came from, it trusts whatever string the model put in that JSON field.
- Conflict between two sources: no code found that detects or resolves disagreement between sources. Grepped for "conflict", "disagree", "contradict" across gpt_researcher/, no hits. The only instruction bearing on this is the same reliability-prioritization prompt text already quoted under QB (prompts.py:306-307), which tells the model to prefer more credible/recent sources when writing, but that is the model's own discretion at generation time, not a check. Absence confirmed.
- Zero results: `ReportGenerator.write_report` has an explicit code-level guard, not a model decision, `_ctx = "\n".join(context) if isinstance(context, list) else str(context or "")`; `if not _ctx.strip(): return f'I could not gather any source material for "{self.researcher.query}". No sources were retrieved...'` (skills/writer.py:82-88), with the comment "Guard against fabricating a report from nothing... don't silently write a confident, sourced-looking report - abstain so it is visible" (writer.py:79-81). This never calls the LLM at all when context is empty. FREE, and this is the single clearest FITS pattern in the whole repo: a pure local check on the assembled context/response shape that aborts and returns a labeled "could not find" answer instead of letting the model fabricate, directly applicable as a pre- or post-check around Shin's one Gemini call (e.g. checking Gemini's grounding metadata is non-empty before trusting the identification/price).

## QD stopping and cost

- Non-deep-research loop: not an iterative "search until good enough" loop at all, it is one fan-out of up to `max_iterations`(=3, default.py:25)+1 sub-queries run concurrently once (`asyncio.gather`, skills/researcher.py:382-387) and combined; there is no re-entry / iteration counter in the standard research flow. FREE/NEEDS OUR OWN SEARCH split as already described under QA.
- Deep-research mode (opt-in, `skills/deep_research.py`) has real recursion with explicit exit conditions: `deep_research(query, breadth, depth, ...)` (deep_research.py:380-398) recurses only `if depth > 1` (deep_research.py:534), each recursion halves breadth with a floor, `new_breadth = max(2, breadth // 2)`, and decrements depth, `new_depth = depth - 1` (deep_research.py:535-536), so it terminates purely by depth reaching 1. Defaults: `"DEEP_RESEARCH_BREADTH": 3`, `"DEEP_RESEARCH_DEPTH": 2`, `"DEEP_RESEARCH_CONCURRENCY": 4` (config/variables/default.py:39-41), the last enforced via `asyncio.Semaphore(self.concurrency_limit)` (deep_research.py:426). It also stops early and does not recurse further if a whole level produces zero successful branches: `if not results: logger.warning("Deep research produced no successful query results at depth=%s; stopping descent."` (deep_research.py:499-514), this is a hard give-up, not a retry-with-different-query. Context is capped at `MAX_CONTEXT_WORDS = 25000` words via `trim_context_to_word_limit`, which trims from the *end* of the list keeping the most recent/last-processed items first (deep_research.py:18, 213-220ff). NEEDS OUR OWN SEARCH (this is a multi-level own-search recursion), but the trim-by-word-budget-from-the-tail pattern and the "stop when nothing came back at this level" guard are FREE local-logic patterns.
- Degraded-answer marking: the zero-context guard in `write_report` (skills/writer.py:82-88, quoted under QC) is the one place a degraded outcome is explicitly labeled rather than silently produced, "I could not gather any source material... I am not able to produce a reliable, sourced report." No other degraded-but-partial state (e.g. "only 1 of 3 sub-queries returned anything") is flagged anywhere in the returned report text; the partial case just silently proceeds with whatever context was gathered. FREE for the labeled zero-case; absence confirmed for the partial case (grepped for "degraded", "partial", "insufficient", no hits tied to report quality).
- LLM retry/backoff: `create_chat_completion` retries up to `max_attempts = 1 if (stream and websocket is not None) else 10` (utils/llm.py:116) on exception or empty response, sleeping `min(2 ** (attempt - 1), 8)` seconds between attempts (utils/llm.py:128-129, 138-139), capped exponential backoff, 1/2/4/8/8/8... seconds. The prompt/messages passed to `provider.get_chat_response(messages, ...)` are never altered between attempts (utils/llm.py:118-122), it is a pure repeat, not a reformulation, confirming the QA finding from the other direction. On final failure it raises `RuntimeError(f"Failed to get response from {llm_provider} API")` (utils/llm.py:157-158) rather than returning a degraded value silently. FREE (local retry/backoff loop; the underlying calls are of course NEEDS OUR OWN SEARCH/LLM-call context, but the backoff mechanism itself is portable).
- Search-call retry: none found at the retriever level beyond the exception-to-empty-list pattern already shown for Tavily (tavily_search.py:153-156), a failed or empty search is caught and turned into `search_response = []`, with no retry loop.
- Per-question cost accounting: `utils/costs.py` defines `estimate_llm_cost`/`calculate_llm_cost` using hardcoded per-model $/token pricing tables (`OPENAI_MODEL_PRICING`, `ANTHROPIC_MODEL_PRICING`, costs.py:31-62) and `estimate_embedding_cost` (imported in context/compression.py:31, called at compression.py:186, 263). Every `create_chat_completion` call threads a `cost_callback` (e.g. researcher.add_costs) that accumulates these estimates (seen throughout report_generation.py, query_processing.py, curator.py, deep_research.py does NOT appear to pass cost_callback in its two direct `create_chat_completion` calls at deep_research.py:335-342 and 367-376, checked both call sites, neither has a `cost_callback` kwarg, so deep-research's own LLM calls are excluded from the running cost total even though the nested `GPTResearcher` sub-researchers it spawns do track costs internally). FREE (pure arithmetic against a static pricing table; not a real API billing readout).
