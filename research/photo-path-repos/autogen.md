# microsoft/autogen
One line: it is a multi-agent orchestration framework (autogen-core message-passing runtime + autogen-agentchat teams/agents + autogen-ext model clients and tool agents) where the agent loop, termination and any critic/reviewer step are all things the caller builds by instantiating library classes and wiring them together, not something the library ships pre-assembled. ## QB. result vetting before belief
- `FREE`, Magentic-One's orchestrator runs a "task ledger" step before work starts: `ORCHESTRATOR_TASK_LEDGER_FACTS_PROMPT` asks the model to sort claims into four buckets: "facts or figures that are GIVEN in the request", "facts that may need to be looked up, and WHERE SPECIFICALLY they might be found", "facts that may need to be derived", and "facts that are recalled from memory, hunches, well-reasoned guesses" (`autogen_agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/_prompts.py:6-19`). This is the closest thing in the codebase to labeling confidence before belief, but it is a self-generated classification by the same model, not a check against an outside source, and it is closer to `FITS` in spirit (one extra reasoning pass on the same input) than to real vetting, I am tagging it `FREE` because the prompt-construction and bucket-sorting itself costs nothing beyond the one inference call it's embedded in, which the orchestrator already needed.

## QC. answer tied to sources, conflict handling
- Critic/reflection pattern, **this is a SAMPLE, not library code.** The only "reviewer"/"critic" agent classes in the whole repo live in documentation notebooks, never in `packages/`:
  - `docs/src/user-guide/core-user-guide/design-patterns/reflection.ipynb` defines a hand-written `CoderAgent` and `ReviewerAgent` (both `RoutedAgent` subclasses from `autogen-core`) that the user must write themselves: define the message dataclasses (`CodeWritingTask`, `CodeReviewTask`, `CodeReviewResult`, cell 2), write each agent's `@message_handler`, and manually `.register()` both agents on a `SingleThreadedAgentRuntime` before publishing the first message (cell 13, `docs/src/user-guide/core-user-guide/design-patterns/reflection.ipynb:207-224`). The reviewer's system prompt, quoted verbatim (`reflection.ipynb:281-163`, cell 8): *"You are a code reviewer. You focus on correctness, efficiency and safety of the code. Respond using the following JSON format: {"correctness": "<Your comments>", "efficiency": "<Your comments>", "safety": "<Your comments>", "approval": "<APPROVE or REVISE>", "suggested_changes": "<Your comments>"}"*.
  - `docs/src/user-guide/agentchat-user-guide/tutorial/teams.ipynb` shows the AgentChat-level version: the user instantiates the ordinary, shipped `AssistantAgent` class twice, naming one `"critic"` and giving it `system_message="Provide constructive feedback. Respond with 'APPROVE' to when your feedbacks are addressed."` (`teams.ipynb:76-80`), then pairs it with `TextMentionTermination("APPROVE")` (`:84`) inside a `RoundRobinGroupChat` (`:87`). `AssistantAgent` itself is library code (`autogen_agentchat/agents/_assistant_agent.py`), but "critic" is not a distinct shipped class or behavior, it is a plain `AssistantAgent` instantiated by the tutorial author with a chosen system-message string and paired with a text-match termination condition the user also has to pick. Confirmed no dedicated class exists: `grep -rn "^class.*Critic\|^class.*Reviewer\|^class.*FactCheck\|^class.*Verifier" python/packages` returned nothing across the entire installable codebase.
  - Verdict for the doc's required call: the fact-checking/critic pattern in AutoGen is a **sample only**. There is no `CriticAgent`, `ReviewerAgent`, or `FactCheckAgent` shipped in `autogen-agentchat`, `autogen-core`, or `autogen-ext`; every instance found is a tutorial notebook that constructs the pattern out of general-purpose classes (`RoutedAgent`, `AssistantAgent`, `TextMentionTermination`) and requires the user to write the critique prompt, the approval keyword, and the termination wiring by hand.
- `FITS`, `AssistantAgent.reflect_on_tool_use`: when true, "another model inference is made using the tool calls and results, and final response is returned" (`autogen_agentchat/src/autogen_agentchat/agents/_assistant_agent.py:141-144`). Default is `False` unless `output_content_type` is set, in which case it defaults to `True` (`:842-848`). This is exactly a second Gemini-style call over the same input/output to produce a judged final answer, the cleanest `FITS` match found in the repo, though AutoGen uses it for tool-result summarization, not fact-checking.
- `FITS`, `CodeExecutorAgent` retry loop (library code, `autogen_agentchat/src/autogen_agentchat/agents/_code_executor_agent.py:548-663`): after a failed code execution, it builds a follow-up prompt and asks the *same* model for a structured decision, quoted verbatim (`:634-638`): *"The most recent code execution resulted in an error:\n{execution_result.output}\n\nShould we attempt to resolve it? Please respond with:\n- A boolean value for 'retry' indicating whether it should be retried.\n- A detailed explanation in 'reason' that identifies the issue, justifies your decision to retry or not, and outlines how you would resolve the error if a retry is attempted."* It requests a structured `RetryDecision` object (`:653`) and only continues if `retry=True`. Default `max_retries_on_error=0` (`:436`), i.e. retries are off unless the caller opts in.
- `FITS`, Magentic-One orchestrator's malformed-JSON retry (library code, `autogen_agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/_magentic_one_orchestrator.py:316-381`): loops up to `self._max_json_retries` (hardcoded to `10`, `:94`) re-asking the same model for its "progress ledger" whenever the JSON fails to parse or is missing required keys, logging `"Failed to parse ledger information, retrying: {ledger_str}"` (`:373`) or `"Invalid ledger format encountered, retrying..."` (`:380`); after 10 failed attempts it raises `ValueError("Failed to parse ledger information after multiple retries.")` (`:382`). The progress-ledger prompt itself (`_prompts.py:59-97`) asks the model to judge, in structured JSON, `is_request_satisfied`, `is_in_loop`, `is_progress_being_made`, `next_speaker`, `instruction_or_question`, this is a self-judgment pass a single grounded call could replicate as a second pass over its own draft answer, but AutoGen uses it to route a multi-agent turn, not to check facts.
- `FREE`, a plain malformed tool-call-argument catch with no retry loop: `AssistantAgent._execute_tool_call` catches `json.JSONDecodeError` and returns `FunctionExecutionResult(content=f"Error: {e}", is_error=True, ...)` straight back into the conversation (`autogen_agentchat/src/autogen_agentchat/agents/_assistant_agent.py:1545-1555`); `autogen_core/src/autogen_core/tool_agent/_tool_agent.py:90-92` does the same, re-raising as `InvalidToolArgumentsException`. Neither location retries on its own; whether the model gets a chance to self-correct depends on whether the caller has turned on `reflect_on_tool_use` (see above), which is what turns this from a dead-end into a second call.
- Conflict handling between two sources: nothing found. Searched `grep -rn "conflict\|disagree\|contradict" python/packages/autogen-agentchat/src python/packages/autogen-ext/src`, hits were all incidental (e.g. "conflicting" in dependency-resolution error text, port-conflict handling in runtime code), none about reconciling two answers about the same fact.

## QD. stopping conditions and cost
- `FREE`, termination conditions are pure local logic evaluated against message history already in memory, no extra model call: `StopMessageTermination`, `MaxMessageTermination(max_messages: int, ...)` (no default, required arg, `autogen_agentchat/src/autogen_agentchat/conditions/_terminations.py:74-89`), `TextMentionTermination(text, sources=None)` (`:123-156`), `TokenUsageTermination(max_total_token=None, max_prompt_token=None, max_completion_token=None)` (`:250-262`, all `None`/unbounded by default, `ValueError` if none given), `HandoffTermination(target)` (`:324`), `TimeoutTermination(timeout_seconds: float)` (no default, `:368-384`, uses `time.monotonic()`), `ExternalTermination` (`:404`), `SourceMatchTermination(sources)` (`:476`), `TextMessageTermination(source=None)` (`:529`), `FunctionCallTermination(function_name)` (`:580`).
- `FREE`, AND/OR combinators: `TerminationCondition.__and__`/`__or__` build `AndTerminationCondition`/`OrTerminationCondition` (`autogen_agentchat/src/autogen_agentchat/base/_termination.py:78-84`, class bodies `:87-140+`), e.g. from the docstring example (`:35-38`): `MaxMessageTermination(10) | TextMentionTermination("TERMINATE")` and `MaxMessageTermination(10) & TextMentionTermination("TERMINATE")`. `AndTerminationCondition` only fires once every child condition has independently fired, concatenating their stop-message contents/sources.
- `FREE`, the base group chat has **no default cap at all**: `RoundRobinGroupChat.__init__` and `SelectorGroupChat.__init__` both default `termination_condition: TerminationCondition | None = None` and `max_turns: int | None = None` (`autogen_agentchat/src/autogen_agentchat/teams/_group_chat/_round_robin_group_chat.py:28-29`, `_selector_group_chat.py:604-605`; also class-level `max_turns: int | None = None` in the config models, `_selector_group_chat.py:352`, `_round_robin_group_chat.py:92`). `_base_group_chat_manager.py:214-222` shows the check is `if self._max_turns is not None: if self._current_turn >= self._max_turns: ...`, so with no termination condition and no max_turns supplied, a `RoundRobinGroupChat`/`SelectorGroupChat` will run until something else (an exception, an external stop) ends it. `SelectorGroupChat` additionally defaults `max_selector_attempts: int = 3` for its own model-based next-speaker vote (`_selector_group_chat.py:616`), separate from the conversation-level termination.
- `FREE`, the one place with real defaults out of the box is `MagenticOneGroupChat`: `max_turns: int | None = 20` and `max_stalls: int = 3` (`autogen_agentchat/src/autogen_agentchat/teams/_group_chat/_magentic_one/_magentic_one_group_chat.py:117,119`, docstring confirms `:52-53`). The orchestrator increments a stall counter whenever `is_progress_being_made` is false or `is_in_loop` is true, and decrements it (floor 0) otherwise (`_magentic_one_orchestrator.py:390-400`); at `self._n_stalls >= self._max_stalls` it triggers a re-plan rather than terminating outright (`:402`). Cost containment here is turn-count and stall-count based, not token- or dollar-based (token cost containment is what `TokenUsageTermination` above is for, and it is off unless the caller wires it in).
